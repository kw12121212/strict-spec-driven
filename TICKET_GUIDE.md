# Ticket Guide: strict-spec-driven

English | [中文](TICKET_GUIDE.zh.md)

**Related:** [Quick Start](QUICKSTART.md) · [Roadmap Guide](ROADMAP_GUIDE.md)

This guide covers the ticket intake workflow end to end: how a raw requirement becomes a strict YAML ticket, how triage decides whether it is already implemented, and how each decision drives the ticket CLI. Tickets are the front door to the workflow — pure requirements captured before any solution, technology choice, or design.

The end-to-end path is:

```text
ticket (pure requirement) -> triage decision -> roadmap milestone -> planned change -> strict change -> spec / tech / code
```

## Where Tickets Live

Tickets live under `.strict-spec-driven/tickets/`:

```text
.strict-spec-driven/tickets/
  INDEX.yaml              # keyed ticket index, regenerated by the CLI
  <ticket-id>.yaml        # one ticket per file
```

A ticket id is **conflict-resistant and content-derived**: a slug of the title plus the first six characters of a SHA-256 hash over the title, problem, and desired outcome. The id is never drawn from a shared sequential counter, so concurrent multi-author intake does not collide on a global number, and the same requirement always resolves to the same id (making creation idempotent).

`INDEX.yaml` is regenerated deterministically from the ticket files on disk whenever a ticket is created or resolved. Keep it a low-churn index — never hand-edit it.

## The Two Intake Skills

Ticket intake is split into two skills on purpose. Capture and triage never run together.

| Skill | Job | When to use |
|---|---|---|
| `/strict-ticket` | **Capture** a raw requirement as a pure-intent ticket through the CLI | You have a requirement but have not decided whether it should become work |
| `/strict-ticket-dispatch` | **Triage** an open ticket: judge implemented-vs-not, then drive `ticket-resolve` | You want to close, promote, or reject an existing ticket |

The boundary is deliberate: the **implemented-vs-not judgment is AI work confined to the triage skill prompt**, while the **CLI performs only the deterministic state transition** and records the decision as an auditable triage record on the ticket. The capture skill never triages, closes, promotes, or rejects, and never creates milestones.

## Ticket Artifact Structure

A ticket is a strict YAML artifact (`strict-spec-driven/ticket/v1`) that records pure intent only.

Example:

```yaml
schema: strict-spec-driven/ticket/v1
schema_version: 1
artifact_type: ticket
schema_file: ../../templates/strict-spec-driven/schemas/ticket.yaml
ticket:
  id: export-changes-as-csv-7f3a9c
  title: Export changes as CSV
requirement:
  problem: Operators cannot get a tabular snapshot of strict changes for sharing outside the tool.
  desired_outcome: A user can obtain a CSV listing of strict changes with their status and milestone.
  intent: Capture the requirement only; the export format, command surface, and implementation are decided downstream.
status: open
created_at: "2026-06-13T00:00:00Z"
labels:
  - reporting
external_tracker:
  label: GitHub
  target: https://example.com/org/repo/issues/42
```

Fields:

| Field | Description |
|---|---|
| `ticket.id` / `ticket.title` | Content-derived id and human-readable title |
| `requirement.problem` | The gap the user is experiencing, in their terms — no proposed fix |
| `requirement.desired_outcome` | What should be true or possible once satisfied, as externally observable behavior |
| `requirement.intent` | Optional acceptance notes: how the user would recognize the requirement as met |
| `status` | Lifecycle status: `open`, `needs_input`, `promoted`, `implemented`, `rejected` |
| `created_at` | Creation timestamp |
| `labels` | Optional categorization labels |
| `external_tracker` | Optional external tracker reference (GitHub/Jira link). A plain reference, not a live integration |
| `provenance.promoted_to` | Milestone id, set when the ticket is promoted |
| `provenance.implemented_by` | Evidence references, recorded when the ticket is closed as implemented |
| `triage_decision` | Triage record: outcome, rationale, decided_at, optional evidence |

`problem` and `desired_outcome` are required. `intent` and everything below `status` is optional.

## Ticket Lifecycle

A ticket starts as `open` and ends in one of three terminal states, set by the triage decision:

```text
              ┌── implemented   ─> implemented   (closes with evidence)
              │
open ─────────┼── not_implemented ─> promoted    (creates a roadmap milestone)
              │
              └── not_wanted    ─> rejected       (rejects or defers)
```

When evidence is ambiguous, contradictory, or spec coverage is too thin to decide confidently, triage does not guess: it leaves the ticket `open` (or moves it to `needs_input`) and defers to the user.

## Triage Outcomes

Triage drives `ticket-resolve` with one of three outcomes. The CLI performs only the deterministic transition for the outcome you decide.

| Outcome (`--outcome`) | Ticket status | What the CLI does |
|---|---|---|
| `implemented` | `implemented` | Records the evidence references in `provenance.implemented_by` |
| `not_wanted` | `rejected` | Preserves the rationale in the auditable triage record; the ticket is never discarded |
| `not_implemented` | `promoted` | Promotes the ticket into a new roadmap milestone skeleton (see below) |

Every decision writes a `triage_decision` record (outcome, rationale, decided_at, and optional evidence) so the reasoning is auditable.

## Promotion Mechanics

On a `not_implemented` decision, the CLI promotes the ticket into a new roadmap milestone. It:

- allocates the next **4-digit milestone number** deterministically, scanning both the roadmap index keys and the milestone files on disk, and **refuses (never overwrites) on collision**;
- materializes a milestone skeleton under `.strict-spec-driven/roadmap/milestones/` with `status: proposed`;
- seeds the milestone `goal` from the ticket's `desired_outcome`;
- leaves `scope.in` / `scope.out` and `done_criteria` as an explicit `REFINEMENT NEEDED` stub — real scope is defined downstream, never fabricated here;
- registers the milestone in `roadmap/INDEX.yaml`;
- sets the ticket to `promoted` and writes **bidirectional links**: `ticket.provenance.promoted_to` and a milestone `source_ticket` back-reference.

Promotion is **idempotent** — re-running triage with `not_implemented` on an already-promoted ticket returns the existing milestone instead of creating a second one.

Promotion requires `.strict-spec-driven/roadmap/INDEX.yaml` to exist. The CLI fails with `roadmap index not found; cannot promote ticket` if it does not.

After a promotion, run `roadmap-sync` to reconcile roadmap state, then hand off scope definition to `/strict-roadmap-milestone` (or `/strict-roadmap-plan`). The dispatch skill never fabricates milestone scope and never decomposes the milestone into changes.

## CLI Command Reference

All ticket state changes go through the CLI. Commands emit JSON and exit non-zero with path-aware diagnostics on failure.

| Command | Signature | Purpose |
|---|---|---|
| `check-workflow-state` | — | Prerequisite for any ticket work; fails if `.strict-spec-driven/` is missing |
| `ticket-create` | `--title <text> --problem <text> --desired-outcome <text> [--intent <text>] [--label <text>]... [--external-label <text> --external-target <text>]` | Scaffolds a new ticket with a conflict-resistant id and `open` status; idempotent on rerun |
| `ticket-list` | — | Lists every ticket's id, title, status, and path in deterministic order |
| `ticket-show <id>` | `<ticket-id>` | Prints one ticket and its path; deterministic not-found error for an unknown id |
| `ticket-validate [<id>]` | `[<ticket-id>]` | Validates one ticket (with id) or all tickets plus the index against the bundled schemas |
| `ticket-resolve <id>` | `--outcome <not_implemented\|implemented\|not_wanted> --rationale <text> [--evidence-label <text> --evidence-target <text>]...` | Records the triage decision and applies the deterministic transition |
| `roadmap-sync` | — | Reconciles roadmap state after a promotion (run before the scope handoff) |

`--external-label` and `--external-target` must be provided together, and each `--evidence-label` must be paired with an `--evidence-target`. Both may repeat.

In-repo invocation form:

```sh
node scripts/strict-spec-driven.js ticket-create --title "..." --problem "..." --desired-outcome "..."
```

When running through an installed skill package, use the exact command form documented in `skills/strict-ticket/SKILL.md` and `skills/strict-ticket-dispatch/SKILL.md`.

## End-to-End Intake Workflow

### Capture (`/strict-ticket`)

1. Run `check-workflow-state`. If `.strict-spec-driven/` is missing, stop and run `/strict-spec-init` first — the skill never runs `init` itself.
2. Elicit pure intent with the user: a **problem** (the gap, in their terms, no fix) and a **desired observable outcome** (what becomes true once satisfied). If the user describes a solution, technology, or design, reflect it back as a problem and an outcome instead.
3. Optionally capture `labels` and an `external_tracker` reference.
4. Restate the problem, desired outcome, and intent back to the user and confirm it contains no solutioning.
5. Create the ticket only with `ticket-create`. Never hand-write ticket YAML or edit the tickets index.
6. Report the ticket id and path. The next step is triage.

### Triage (`/strict-ticket-dispatch`)

1. Select the ticket — if the user did not name one, run `ticket-list`, choose an open ticket, and `ticket-show` it.
2. Gather evidence by reading `.strict-spec-driven/specs/INDEX.yaml`, the relevant main specs, spec-to-code mappings, the mapped implementation and test files, and repository docs (README, QUICKSTART, guides). Note the concrete spec, code, and doc references your judgment relies on.
3. Form a judgment: `implemented`, `not_implemented`, or `not_wanted`. If evidence is ambiguous or thin, defer and leave the ticket open.
4. Apply the decision only through `ticket-resolve` — never by editing ticket YAML.
5. After a promotion, run `roadmap-sync`, then hand off to `/strict-roadmap-milestone` for real scope definition.
6. Report the decision, the evidence it relied on, the resulting ticket status, and (for a promotion) the created milestone id.

## Quick Examples

```sh
# Capture
node scripts/strict-spec-driven.js ticket-create \
  --title "Export changes as CSV" \
  --problem "Operators cannot get a tabular snapshot of strict changes for sharing outside the tool." \
  --desired-outcome "A user can obtain a CSV listing of strict changes with their status and milestone." \
  --intent "Capture the requirement only; format and command surface are decided downstream." \
  --label reporting \
  --external-label GitHub --external-target https://example.com/org/repo/issues/42

# Inspect
node scripts/strict-spec-driven.js ticket-list
node scripts/strict-spec-driven.js ticket-show export-changes-as-csv-7f3a9c
node scripts/strict-spec-driven.js ticket-validate
node scripts/strict-spec-driven.js ticket-validate export-changes-as-csv-7f3a9c

# Triage — pick one outcome:

# Already implemented: close with evidence
node scripts/strict-spec-driven.js ticket-resolve export-changes-as-csv-7f3a9c \
  --outcome implemented \
  --rationale "CSV export already exists in the operations command surface." \
  --evidence-label spec --evidence-target .strict-spec-driven/specs/operations/domain-behavior.yaml \
  --evidence-label code --evidence-target src/cli/cmd-operations.ts

# Genuinely new: promote into a roadmap milestone, then roadmap-sync + /strict-roadmap-milestone
node scripts/strict-spec-driven.js ticket-resolve export-changes-as-csv-7f3a9c \
  --outcome not_implemented \
  --rationale "No CSV export capability exists anywhere in the workflow today."

# Reject or defer
node scripts/strict-spec-driven.js ticket-resolve export-changes-as-csv-7f3a9c \
  --outcome not_wanted \
  --rationale "Overlaps with the upcoming reporting rewrite; not in scope this cycle."
```

## Rules and Boundaries

- Capture pure intent only — problem, desired outcome, and acceptance notes. Never a solution, technology choice, or design.
- Create and modify tickets only through the ticket CLI commands. Never hand-write ticket YAML or edit the tickets index.
- Keep the implemented-vs-not judgment in the triage skill prompt; keep every state transition in the CLI.
- Defer to the user and leave the ticket open or `needs_input` when evidence is ambiguous — never guess a transition.
- After a promotion, run `roadmap-sync` and hand scope definition to `/strict-roadmap-milestone`. Never fabricate milestone scope or decompose it into changes.
