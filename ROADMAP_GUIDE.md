# Roadmap Guide: strict-spec-driven

English | [中文](ROADMAP_GUIDE.zh.md)

**Quick start:** [English](ROADMAP_QUICKSTART.md) | [中文](ROADMAP_QUICKSTART.zh.md)

This guide covers the contributor-facing roadmap workflow: milestone structure, standalone planned-change files, roadmap skill commands, and how to keep team collaboration merge-friendly.

## Roadmap Location

The strict roadmap lives under `.strict-spec-driven/roadmap/`:

```text
.strict-spec-driven/roadmap/
  INDEX.yaml                 # keyed milestone index
  milestones/
    0001-some-milestone.yaml
    0002-another-milestone.yaml
  planned-changes/
    0001-some-milestone-add-work.yaml
    0001-some-milestone-fix-docs.yaml
```

The preferred layout is:

- `INDEX.yaml` stays a low-churn milestone index
- milestone files hold durable milestone metadata and keep `planned_changes: {}` after migration
- standalone planned-change files under `planned-changes/` are the normal team work-item surface

If your project still has a legacy `.spec-driven/roadmap/` directory left over from before migration, treat it as migration history only. The strict CLI reads and rewrites `.strict-spec-driven/roadmap/` as the canonical roadmap source.

## Roadmap Index

`INDEX.yaml` is a keyed milestone map. Each entry identifies one milestone file and its declared status:

```yaml
schema: strict-spec-driven/roadmap-index/v2
schema_version: 2
artifact_type: roadmap_index
schema_file: ../../templates/strict-spec-driven/schemas/roadmap-index.yaml
milestones:
  0001-example-milestone:
    title: Example Milestone
    path: roadmap/milestones/0001-example-milestone.yaml
    status: proposed
```

The index is regenerated by `roadmap-sync`. Keep it simple and avoid using it as a high-churn work-item registry.

## Milestone Files

Milestone files define durable planning context: goal, scope, done criteria, dependencies, risks, notes, and the milestone's declared status.

Example milestone:

```yaml
schema: strict-spec-driven/roadmap-milestone/v2
schema_version: 2
artifact_type: roadmap_milestone
schema_file: ../../templates/strict-spec-driven/schemas/roadmap-milestone.yaml
milestone:
  0001-example-milestone:
    title: Example Milestone
goal: Define one milestone goal.
scope:
  in:
    - Planned strict workflow behavior.
  out:
    - Unrelated behavior.
done_criteria:
  - The planned behavior is implemented and verified.
planned_changes: {}
dependencies: []
risks: []
status: proposed
notes: []
details: >-
  Longer planning context for the milestone as a whole.
```

Keep `planned_changes: {}` on milestone files. Non-empty inline entries are treated as legacy roadmap data that must be materialized before normal roadmap commands will succeed.

## Standalone Planned-Change Files

Use standalone planned-change artifacts under `.strict-spec-driven/roadmap/planned-changes/` as the default way to add or edit roadmap work.

CLI code owns the YAML shape and filesystem placement of roadmap artifacts. AI workflows express every milestone and planned-change mutation through `roadmap-generate` named arguments — never through raw YAML text. Consult `strict-spec-cli roadmap-generate --help --json` for the full argument contract, and inspect the artifact shapes with `schema-show roadmap-milestone`, `schema-show planned-change`, and the matching `sample-show` keys. The `schema_file` each roadmap artifact declares resolves beneath the shared schema cache root `~/.strict-spec-schemas/` (or `STRICT_SPEC_SCHEMA_CACHE_DIR`) in installed environments. Create and update planned changes through the CLI:

```sh
strict-spec-cli roadmap-generate planned-change --milestone 0001-user-auth --id add-session-model --summary "Add session data model and storage." --details "..."
```

The command writes the artifact at its canonical filename `<milestone-id>-<planned-change-id>.yaml` (the milestone prefix is not duplicated when the planned-change id already starts with it). Filename order is semantically meaningful — `roadmap-recommend` picks the first eligible planned change in filename order — so an active planned-change file with a non-canonical basename is a blocking `roadmap-status`/`roadmap-sync` diagnostic. Repair misnamed legacy files with `roadmap-sync --fix-names`; never pick planned-change filenames by hand. Archived planned-change files are exempt.

Example planned-change file:

```yaml
schema: strict-spec-driven/planned-change/v1
schema_version: 1
artifact_type: planned_change
schema_file: ../../templates/strict-spec-driven/schemas/planned-change.yaml
planned_change:
  id: add-session-model
  milestone: 0001-user-auth
status: planned
summary: Add session data model and storage.
details: >-
  Store the session workflow as an independent roadmap item so one contributor can
  update this file without rewriting the milestone file.
depends_on: []
team:
  owner: alice
  reviewers:
    - bob
  blocked:
    status: false
  labels:
    - roadmap
  external_refs:
    - label: Tracking issue
      target: https://example.com/issues/123
```

Required fields:

| Field | Description |
|---|---|
| `planned_change.id` | Kebab-case planned change identity |
| `planned_change.milestone` | Owning milestone ID |
| `status` | `planned` or `complete` |
| `summary` | Short work summary |
| `details` | Focused planning context for this work item |
| `depends_on` | IDs of prerequisite planned changes |

Optional `team` metadata is advisory only. `owner`, `reviewers`, `blocked`, `labels`, and `external_refs` help coordination, but they are not locks and do not replace Git or code review.

## Legacy Inline `planned_changes`

Non-empty milestone `planned_changes` mappings are treated as legacy roadmap data.

`roadmap-status` and ordinary `roadmap-sync` fail fast when they detect inline entries and tell you to materialize them first.

To convert legacy inline milestone entries into standalone planned-change files, run:

```sh
strict-spec-cli roadmap-sync --materialize-planned-changes
```

That conversion writes planned-change files under `.strict-spec-driven/roadmap/planned-changes/`, removes the converted entries from the milestone file, and then reruns roadmap reconciliation on the materialized layout.

## Conflict-Resistant Team Workflow

The roadmap is designed to reduce merge conflicts through artifact granularity:

1. Keep milestone files focused on milestone-wide planning context.
2. Put day-to-day roadmap work items in standalone planned-change files.
3. Let each contributor own their planned-change file instead of appending to the same milestone map, updating it through `roadmap-generate planned-change` (a human may also maintain their own file by hand). <!-- human-manual-edit -->
4. Keep `INDEX.yaml` as a shared milestone list rather than a coordination surface for every work item.

Recommended habits:

- Prefer one planned change per file.
- Treat team metadata as advisory coordination hints, not exclusive claims.
- After merges, rerun `/strict-roadmap-transition sync` or `strict-spec-cli roadmap-sync`.
- After archiving a roadmap-backed strict change, rerun `roadmap-sync` so planned-change and milestone status are reconciled from workflow state.
- Use external tracker references only as optional supporting context. GitHub Issues, Jira, Linear, and similar tools are not required sources of truth for the strict roadmap.

## Roadmap Skill Commands

Use these Claude Code slash commands to work with the roadmap:

### `/strict-roadmap-recommend`

Reads roadmap state and recommends the best next planned change to work on from standalone planned-change files. The command scaffolds one normal strict change under `.strict-spec-driven/changes/` without stopping for extra confirmation.

After the scaffold validates, the default next step is `/strict-spec-auto`. If the recommendation produces open questions, those questions are recorded in `questions.yaml` and surfaced before implementation.

## Change Intake Question Gate

Proposal-oriented workflows must answer a short checklist before implementation.
Agents should use the active request, selected roadmap planned-change details,
main specs, technical standards, existing change artifacts,
repository search results, and deterministic CLI output as evidence before
asking the human anything.

The checklist intents are:

- What do you want changed?
- Why is this worth doing?
- What should be included?
- What should be left out?
- What existing behavior must stay the same?
- Where does this likely live: code, specs, templates, skills, docs, config, or another named repository artifact family found during discovery?
- How will we prove it works?
- Could this affect existing users, saved data, APIs, security, privacy, performance, release, or rollback?
- Is anything blocked by a roadmap item, active change, service, credential, or outside dependency?
- Which existing technical rules apply, or do we need a new rule for this change?

If discovery answers a checklist item, the agent uses that evidence and does not
ask again. If a required answer is still unknown, proposal creation records it
in `questions.yaml.open` with what is unknown, why it matters, the affected
scope or testing decision, and the recommended answer or options.

Roadmap-backed proposal flows treat the selected standalone planned-change
`summary`, `details`, `depends_on`, labels, and owning
milestone `details` as valid evidence for the same checklist. Complete roadmap
detail should be carried into generated proposal artifacts instead of becoming a
duplicate human question. Thin roadmap detail, missing implementation/test/spec
impact, dependency uncertainty, or technical-standard uncertainty should become
localized `questions.yaml.open` blockers before implementation.

Human-facing question text, context, recommendations, options, and summaries
must use the `preferred_human_language` from `.strict-spec-driven/config.yaml`
unless the active user message explicitly asks for a different language. Stable
technical values such as question ids, artifact fields, schema names, command
names, and file paths remain stable identifiers and are not localized.

Implementation handoff stops while required entries remain in
`questions.yaml.open`. The unresolved questions must be resolved and moved into
the resolved question state before `/strict-spec-auto`, `/strict-spec-apply`, or
another implementation workflow continues.

### `/strict-roadmap-review`

Reviews one incomplete milestone's goal, scope, done criteria, dependencies, risks, and planned-change `details`, applies fixes through `roadmap-generate milestone` and `roadmap-generate planned-change` named arguments, then reruns `roadmap-sync`.

```text
/strict-roadmap-review 0001-user-auth
```

### `/strict-roadmap-plan`

Creates or restructures the roadmap when you need to add, reorder, or rewrite milestones.

### `/strict-roadmap-transition sync`

Reconciles roadmap state against strict workflow state. `sync` is one of the eight operations `/strict-roadmap-transition` performs; the others are `pause`, `resume`, `defer`, `refine`, `move`, `reopen`, and `archive`, each selected by naming it explicitly. Milestone reordering is not among them — it has its own skill, `/strict-roadmap-reorder`.

It:

- regenerates `INDEX.yaml`
- reconciles milestone status
- reconciles standalone planned-change status
- rejects legacy inline milestone `planned_changes` unless you explicitly request materialization

Run this after merges and after archiving roadmap-backed work:

```text
/strict-roadmap-transition sync
```

CLI form:

```sh
strict-spec-cli roadmap-sync
```

### `/strict-roadmap-reorder`

Changes one active milestone's position in roadmap order. Order comes from the
optional integer `order` field, never from the milestone id prefix or the
filename, so the skill resolves the request into exactly one of `--before`,
`--after`, or `--order` and runs the command once. When no integer gap remains
between the requested neighbours, run `roadmap-renumber` first, then rerun the
reorder.

The skill stops for an explicit human answer when the new position would place
a milestone before work it depends on; the command itself does not read
`depends_on` edges.

CLI form:

```sh
strict-spec-cli roadmap-reorder <milestone-id> --after <neighbor-id>
```

## How to Add a Planned Change

Preferred path:

1. Open the owning milestone file under `.strict-spec-driven/roadmap/milestones/` and confirm its goal, scope, and done criteria still describe the work area correctly.
2. Run `strict-spec-cli roadmap-generate planned-change --milestone <milestone-id> --id <planned-change-id> --summary "..." --details "..."` — the CLI creates the file at its canonical `<milestone-id>-<planned-change-id>.yaml` name under `.strict-spec-driven/roadmap/planned-changes/`.
3. Add `--depends-on <planned-change-id>` arguments and optional `team` metadata if they help coordination.
4. Run `/strict-roadmap-transition sync` to validate the roadmap and refresh derived state.

Example:

```yaml
schema: strict-spec-driven/planned-change/v1
schema_version: 1
artifact_type: planned_change
schema_file: ../../templates/strict-spec-driven/schemas/planned-change.yaml
planned_change:
  id: my-new-change
  milestone: 0001-example-milestone
status: planned
summary: Add one new roadmap work item.
details: >-
  Explain the focused planning context for this one change.
depends_on: []
```

## How to Complete a Planned Change

Planned-change completion is derived from archived strict workflow state.

1. Scaffold the change with `/strict-roadmap-recommend`.
2. Implement it with `/strict-spec-auto` or the manual strict lifecycle commands.
3. Archive the strict change.
4. Run `/strict-roadmap-transition sync`.
5. Confirm `roadmap-status` shows the planned change and milestone state you expect.

Do not hand-edit roadmap completion state after implementation. Let the strict workflow archive plus `roadmap-sync` update the roadmap artifacts.

## Checking Roadmap State

For a human-readable panorama of milestone status plus grouped planned-change detail:

```sh
strict-spec-cli roadmap-overview
```

For machine-readable validation output:

```sh
strict-spec-cli roadmap-status
```

`roadmap-overview` prints a milestone summary table followed by per-milestone planned-change detail.

`roadmap-status` reports each milestone's declared and derived status, each planned change's source file path and workflow state, and any mismatches or cross-file validation problems in JSON.
