# Roadmap Guide: strict-spec-driven

English | [中文](ROADMAP_GUIDE.zh.md)

**Quick start:** [English](ROADMAP_QUICKSTART.md) | [中文](ROADMAP_QUICKSTART.zh.md)

This guide covers the contributor-facing roadmap workflow: milestone structure, standalone planned-change files, roadmap skill commands, and how to keep team collaboration merge-friendly.

## Roadmap Location

The strict roadmap lives under `.strict-spec-driven/roadmap/`:

```text
.strict-spec-driven/roadmap/
  INDEX.yaml                 # keyed milestone index
  milestones/
    0001-some-milestone.yaml
    0002-another-milestone.yaml
  planned-changes/
    0001-some-milestone-add-work.yaml
    0001-some-milestone-fix-docs.yaml
```

The preferred layout is:

- `INDEX.yaml` stays a low-churn milestone index
- milestone files hold durable milestone metadata and keep `planned_changes: {}` after migration
- standalone planned-change files under `planned-changes/` are the normal team work-item surface

If a preserved bootstrap `.spec-driven/roadmap/` directory also exists, treat it as migration history only. The strict CLI reads and rewrites `.strict-spec-driven/roadmap/` as the canonical roadmap source.

## Roadmap Index

`INDEX.yaml` is a keyed milestone map. Each entry identifies one milestone file and its declared status:

```yaml
schema: strict-spec-driven/roadmap-index/v2
schema_version: 2
artifact_type: roadmap_index
schema_file: ../../templates/strict-spec-driven/schemas/roadmap-index.yaml
milestones:
  0001-example-milestone:
    title: Example Milestone
    path: roadmap/milestones/0001-example-milestone.yaml
    status: proposed
```

The index is regenerated by `roadmap-sync`. Keep it simple and avoid using it as a high-churn work-item registry.

## Milestone Files

Milestone files define durable planning context: goal, scope, done criteria, dependencies, risks, notes, and the milestone's declared status.

Example milestone:

```yaml
schema: strict-spec-driven/roadmap-milestone/v2
schema_version: 2
artifact_type: roadmap_milestone
schema_file: ../../templates/strict-spec-driven/schemas/roadmap-milestone.yaml
milestone:
  0001-example-milestone:
    title: Example Milestone
goal: Define one milestone goal.
scope:
  in:
    - Planned strict workflow behavior.
  out:
    - Unrelated behavior.
done_criteria:
  - The planned behavior is implemented and verified.
planned_changes: {}
dependencies: []
risks: []
status: proposed
notes: []
details: >-
  Longer planning context for the milestone as a whole.
```

Keep `planned_changes: {}` on milestone files. Non-empty inline entries are treated as legacy roadmap data that must be materialized before normal roadmap commands will succeed.

## Standalone Planned-Change Files

Use standalone planned-change artifacts under `.strict-spec-driven/roadmap/planned-changes/` as the default way to add or edit roadmap work.

Example planned-change file:

```yaml
schema: strict-spec-driven/planned-change/v1
schema_version: 1
artifact_type: planned_change
schema_file: ../../templates/strict-spec-driven/schemas/planned-change.yaml
planned_change:
  id: add-session-model
  milestone: 0001-user-auth
status: planned
summary: Add session data model and storage.
details: >-
  Store the session workflow as an independent roadmap item so one contributor can
  update this file without rewriting the milestone file.
depends_on: []
team:
  owner: alice
  reviewers:
    - bob
  blocked:
    status: false
  labels:
    - roadmap
  external_refs:
    - label: Tracking issue
      target: https://example.com/issues/123
```

Required fields:

| Field | Description |
|---|---|
| `planned_change.id` | Kebab-case planned change identity |
| `planned_change.milestone` | Owning milestone ID |
| `status` | `planned` or `complete` |
| `summary` | Short work summary |
| `details` | Focused planning context for this work item |
| `depends_on` | IDs of prerequisite planned changes |

Optional `team` metadata is advisory only. `owner`, `reviewers`, `blocked`, `labels`, and `external_refs` help coordination, but they are not locks and do not replace Git or code review.

## Legacy Inline `planned_changes`

Non-empty milestone `planned_changes` mappings are treated as legacy roadmap data.

`roadmap-status` and ordinary `roadmap-sync` fail fast when they detect inline entries and tell you to materialize them first.

To convert legacy inline milestone entries into standalone planned-change files, run:

```sh
node scripts/strict-spec-driven.js roadmap-sync --materialize-planned-changes
```

That conversion writes planned-change files under `.strict-spec-driven/roadmap/planned-changes/`, removes the converted entries from the milestone file, and then reruns roadmap reconciliation on the materialized layout. If you are running through an installed skill package, use the exact command form documented in `skills/strict-roadmap-sync/SKILL.md`.

## Conflict-Resistant Team Workflow

The roadmap is designed to reduce merge conflicts through artifact granularity:

1. Keep milestone files focused on milestone-wide planning context.
2. Put day-to-day roadmap work items in standalone planned-change files.
3. Let each contributor edit the planned-change file they own instead of appending to the same milestone map.
4. Keep `INDEX.yaml` as a shared milestone list rather than a coordination surface for every work item.

Recommended habits:

- Prefer one planned change per file.
- Treat team metadata as advisory coordination hints, not exclusive claims.
- After merges, rerun `/strict-roadmap-sync` or `node scripts/strict-spec-driven.js roadmap-sync`.
- After archiving a roadmap-backed strict change, rerun `roadmap-sync` so planned-change and milestone status are reconciled from workflow state.
- Use external tracker references only as optional supporting context. GitHub Issues, Jira, Linear, and similar tools are not required sources of truth for the strict roadmap.

## Roadmap Skill Commands

Use these Claude Code slash commands to work with the roadmap:

### `/strict-roadmap-recommend`

Reads roadmap state and recommends the best next planned change to work on from standalone planned-change files. The command scaffolds one normal strict change under `.strict-spec-driven/changes/` without stopping for extra confirmation.

After the scaffold validates, the default next step is `/strict-spec-auto`. If the recommendation produces open questions, those questions are recorded in `questions.yaml` and surfaced before implementation.

### `/strict-roadmap-propose`

Turns a specific planned change into a strict change scaffold. Use when you already know which roadmap work item you want.

```text
/strict-roadmap-propose add-session-model
```

### `/strict-roadmap-milestone`

Refines one milestone's goal, scope, done criteria, dependencies, risks, notes, and `details` without restructuring the entire roadmap.

```text
/strict-roadmap-milestone 0001-user-auth
```

### `/strict-roadmap-plan`

Creates or restructures the roadmap when you need to add, reorder, or rewrite milestones.

### `/strict-roadmap-sync`

Reconciles roadmap state against strict workflow state.

It:

- regenerates `INDEX.yaml`
- reconciles milestone status
- reconciles standalone planned-change status
- rejects legacy inline milestone `planned_changes` unless you explicitly request materialization

Run this after merges and after archiving roadmap-backed work:

```text
/strict-roadmap-sync
```

CLI form:

```sh
node scripts/strict-spec-driven.js roadmap-sync
```

## How to Add a Planned Change

Preferred path:

1. Open the owning milestone file under `.strict-spec-driven/roadmap/milestones/` and confirm its goal, scope, and done criteria still describe the work area correctly.
2. Create a new standalone file under `.strict-spec-driven/roadmap/planned-changes/`.
3. Set `planned_change.id`, `planned_change.milestone`, `status`, `summary`, `details`, and `depends_on`.
4. Add optional `team` metadata if it helps coordination.
5. Run `/strict-roadmap-sync` to validate the roadmap and refresh derived state.

Example:

```yaml
schema: strict-spec-driven/planned-change/v1
schema_version: 1
artifact_type: planned_change
schema_file: ../../templates/strict-spec-driven/schemas/planned-change.yaml
planned_change:
  id: my-new-change
  milestone: 0001-example-milestone
status: planned
summary: Add one new roadmap work item.
details: >-
  Explain the focused planning context for this one change.
depends_on: []
```

## How to Complete a Planned Change

Planned-change completion is derived from archived strict workflow state.

1. Scaffold the change with `/strict-roadmap-recommend` or `/strict-roadmap-propose`.
2. Implement it with `/strict-spec-auto` or the manual strict lifecycle commands.
3. Archive the strict change.
4. Run `/strict-roadmap-sync`.
5. Confirm `roadmap-status` shows the planned change and milestone state you expect.

Do not hand-edit roadmap completion state after implementation. Let the strict workflow archive plus `roadmap-sync` update the roadmap artifacts.

## Checking Roadmap State

```sh
node scripts/strict-spec-driven.js roadmap-status
```

The command reports each milestone's declared and derived status, each planned change's workflow state, and any mismatches or cross-file validation problems.
