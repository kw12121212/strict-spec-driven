# strict-spec-driven

English | [中文](README.zh.md)

**Documentation:** [Quick Start](QUICKSTART.md) · [Roadmap Quick Start](ROADMAP_QUICKSTART.md) · [Roadmap Guide](ROADMAP_GUIDE.md) · [Dev Sessions](DEV_SESSIONS.md) · [Debug Sessions](DEBUG_SESSIONS.md) · [RTK](RTK.md)

`strict-spec-driven` is a YAML-first spec-driven development workflow. It provides the spec-driven lifecycle (propose → apply → verify → skill-driven code review → archive) with Agent Skills integration, converting workflow artifacts — specs, changes, roadmap, tasks, questions — into strict YAML schemas enforced by deterministic scripts.

`SKILL.md` files remain Markdown because that is the Agent Skills packaging format requirement. What changes is the artifact format those skills generate and consume.

## Directory Structure

| Directory | Role |
|---|---|
| `.strict-spec-driven/` | Active strict workflow state |
| `.strict-spec-driven/changes/` | Active change directories |
| `.strict-spec-driven/changes/archive/` | Archived changes |
| `.strict-spec-driven/roadmap/` | Strict YAML roadmap artifacts |
| `.strict-spec-driven/roadmap/planned-changes/` | Preferred standalone roadmap work-item files |
| `.strict-spec-driven/specs/` | Strict YAML main spec files |
| `.spec-driven/` | Bootstrap and legacy workflow input only |
| `templates/strict-spec-driven/schemas/` | Bundled strict YAML schema files |
| `examples/strict-spec-driven/` | Repository reference minimal valid YAML examples |
| `templates/strict-spec-driven/scaffold/` | Scaffold templates used by `init` and `propose` |
| `skills/` | Strict skill packages (`strict-spec-*` and `strict-roadmap-*`) |
| `src/` | TypeScript CLI source |
| `dist/` | Compiled output (generated by build) |

`.spec-driven/` is preserved as bootstrap and migration input. It is not the active workflow directory after strict migration. Do not treat `.spec-driven/` and `.strict-spec-driven/` as equivalent active targets, and do not treat `.spec-driven/roadmap/` as the canonical roadmap once `.strict-spec-driven/roadmap/` exists.

## Strict Command Surface

### CLI: `strict-spec-driven`

Subcommands available after `bun run build` (or via installed `node dist/strict-spec-cli.js`):

| Subcommand | Purpose |
|---|---|
| `init` | Scaffold `.strict-spec-driven/` in a project |
| `propose <name>` | Create a new strict change scaffold |
| `apply <name>` | Complete the next pending task in a change |
| `verify <name>` | Validate a change's artifacts and task completion |
| `archive <name>` | Merge delta specs and move change to archive |
| `ship <name>` | Read archived change summary for git commit handoff |
| `migrate` | Convert `.spec-driven/` bootstrap state to `.strict-spec-driven/` |
| `list` | Report active and archived changes |
| `modify [<name>]` | List editable artifact paths for a change |
| `cancel <name>` | Remove an active change (archived changes are protected) |
| `maintenance` | Run configured repository maintenance checks |
| `roadmap-status` | Validate and report strict roadmap state |
| `roadmap-overview` | Print a human-readable roadmap overview table |
| `roadmap-sync` | Reconcile and regenerate strict roadmap index |
| `verify-spec-mappings` | Audit spec implementation and test mapping coverage |
| `validate-skills` | Validate strict skill packaging metadata and command symlinks |
| `schema-list` | List bundled strict schema asset keys |
| `schema-show <name>` | Print a bundled strict schema asset |
| `template-list` | List bundled template and schema asset keys |
| `template-show <key>` | Print a bundled template or schema asset |
| `debug-session-create <id>` | Create a strict debug-session artifact and evidence directory |
| `debug-session-validate <id\|path>` | Validate a strict debug-session artifact |

### Skills: `strict-spec-*` and `strict-roadmap-*`

Skills are Agent Skills packages installed via `install.sh`. Invoke them in Claude Code using their slash-command names:

**Strict spec workflow skills** (`strict-spec-*`):

| Slash command | Purpose |
|---|---|
| `/strict-spec-init` | Initialize strict workflow in a project |
| `/strict-spec-propose` | Propose a new change |
| `/strict-spec-apply` | Implement tasks in a change |
| `/strict-spec-verify` | Verify a change is complete |
| `/strict-spec-review` | Evidence-based code-quality review of a change |
| `/strict-spec-archive` | Archive a completed change |
| `/strict-spec-auto` | End-to-end automated change lifecycle |
| `/strict-spec-ship` | Ship an archived change via git commit |
| `/strict-spec-migrate` | Migrate bootstrap state to strict YAML |
| `/strict-spec-brainstorm` | Brainstorm a change idea before proposing |
| `/strict-spec-modify` | Modify an existing change's artifacts |
| `/strict-spec-cancel` | Cancel an active change |
| `/strict-spec-debug-session` | Run a structured debugging investigation |
| `/strict-spec-simple-task` | Lightweight ad-hoc task without full lifecycle |
| `/strict-spec-spec-edit` | Edit main spec files directly |
| `/strict-spec-sync-specs` | Synchronize specs with code drift |
| `/strict-spec-resync-code-mapping` | Repair spec implementation and test mappings |
| `/strict-spec-maintenance` | Run repository maintenance workflow |

**Strict roadmap skills** (`strict-roadmap-*`):

| Slash command | Purpose |
|---|---|
| `/strict-roadmap-recommend` | Recommend the next planned change from the roadmap |
| `/strict-roadmap-propose` | Turn a roadmap planned change into a change scaffold |
| `/strict-roadmap-milestone` | Refine a roadmap milestone |
| `/strict-roadmap-plan` | Create or restructure the roadmap |
| `/strict-roadmap-sync` | Reconcile roadmap milestone and change state |

The roadmap docs describe the preferred split-file collaboration model: keep milestone files and `INDEX.yaml` low churn, store day-to-day roadmap work in `.strict-spec-driven/roadmap/planned-changes/`, rerun `roadmap-sync` after merges or archive handoff, and treat external tracker references as optional context rather than required source of truth.

## Schema and Example Assets

Bundled strict YAML schema files live under `templates/strict-spec-driven/schemas/`. Minimal valid examples live under `examples/strict-spec-driven/` as repository reference assets. These are separate from `.strict-spec-driven/` workflow state.

The schema registry at `templates/strict-spec-driven/schemas/schema-registry.yaml` indexes all supported strict artifact families.

The CLI also embeds bundled schema and scaffold assets so installed skills do not need a per-skill `templates` symlink. Agents can inspect embedded contracts with:

```sh
node {{SKILL_DIR}}/scripts/strict-spec-driven.js schema-list
node {{SKILL_DIR}}/scripts/strict-spec-driven.js schema-show change-proposal
node {{SKILL_DIR}}/scripts/strict-spec-driven.js template-show scaffold/changes/proposal.yaml
```

## Development Sessions

A development session declaration at `.strict-spec-driven/dev-session.yaml` tells agents what local services to start, how to wait for readiness, which browser URLs to open for smoke testing, and how to stop services cleanly — all from a single YAML file. Strict lifecycle skills check this file automatically when it exists.

See [DEV_SESSIONS.md](DEV_SESSIONS.md) for the full reference: declaration syntax, schema fields, CLI commands (`dev-session-plan`, `dev-session-start`, `dev-session-status`, `dev-session-logs`, `dev-session-stop`, `dev-session-trial`), generated helper scripts, browser trial evidence, and secret-handling rules.

## Debug Sessions

A debug session under `.strict-spec-driven/debug-sessions/<session-id>/` records a single investigation with reproduction steps, evidence files, hypotheses, findings, human checkpoints, manual actions, dev-session lifecycle evidence, CDP health, replay commands, and verification results. It is intended for Web API, frontend, Electron desktop, and CDP-access debugging.

See [DEBUG_SESSIONS.md](DEBUG_SESSIONS.md) for the artifact layout, CLI commands (`debug-session-create`, `debug-session-validate`), layer localization rules, and secret-handling guidance.

## Migration Boundaries

The `migrate` subcommand and `/strict-spec-migrate` skill convert supported legacy `.spec-driven/` Markdown artifacts into `.strict-spec-driven/` YAML artifacts. The source `.spec-driven/` directory is not modified. Unsupported or ambiguous legacy shapes are reported as manual follow-up items in the migration report.

After migration, `.strict-spec-driven/` is the active workflow state. `.spec-driven/` remains as bootstrap or legacy history and is not treated as a valid strict workflow target.

## Self-Hosting Status

This repository is self-hosted on the strict workflow. `.strict-spec-driven/` contains the active strict specs, roadmap, and change history. `.spec-driven/` is preserved as the bootstrap migration input.

## Development

**Prerequisites:** [Bun](https://bun.sh) (runtime and package manager), Node.js (for `npx`)

**Build:**
```sh
bun run build
```
Compiles `src/` to `dist/` via TypeScript and copies `templates/` and `scripts/` into `dist/`.

**Test:**
```sh
bun test/run.ts
```
Runs the test suite against compiled `dist/` output.

**Validate skills:**
```sh
bun run validate-skills
```
Validates all strict skill packages for metadata, command references, and required command script access.

**Conventions:**
- Use a structured YAML parser — never ad-hoc string processing for core artifact data.
- Spec changes should be reflected in `.strict-spec-driven/specs/` before implementation.
- Run `bun run build && bun test/run.ts` after any source change.
- Read existing code before modifying it; implement only what the current task requires.
